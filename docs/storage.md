# 分割保存

```text
data/
├── store.json                 # 共通データとメッセージファイルの参照
├── store.legacy-<UUID>.json   # 初回移行前の全データ
├── line/
│   └── <Contact ID>/
│       └── messages-<内容のハッシュ>.json
└── slack/
    └── <Contact ID>/
        └── messages-<内容のハッシュ>.json
```

Contact IDはアプリ内部のID。表示名の変更や同名ユーザーで保存先が衝突しない。
通常のUUIDはそのままフォルダ名に使い、特殊文字を含むIDは安全な文字列へ変換する。
同じ人でもLINEとSlackは別Contactであり、別々に保存する。

## 役割

- store.json: Contact、Conversation、Reminder、カスタムタブ、メッセージファイル参照、保存順。
- messages-*.json: そのContactとの受信・送信メッセージ。共通Message形式。
- splitStore.js: 分割保存・読み込み・旧形式からの移行。
- jsonStore.js: 更新キュー・検証・管理ファイルの置換。RepositoryとAPIの共通状態形式は維持する。

ファイル分割は保存単位の変更。起動時は全履歴をメモリへ読み込む。
MVPの単一Backendプロセスを前提とし、大規模DBや複数プロセスの同時書き込みには対応しない。
お気に入りやタブだけの更新では、内容が同じメッセージファイルを再利用する。

## 更新の確定

1. 変更したContactの履歴を新しいファイル名で保存する。
2. 新しい参照と共通データを管理ファイルの一時ファイルへ保存する。
3. 一時ファイルをstore.jsonへrenameし、更新を確定する。
4. 参照されなくなった旧メッセージファイルを削除する。

確定前の保存失敗では、旧管理ファイル・旧履歴・メモリ状態を維持する。
確定後の旧ファイル削除失敗は保存失敗として扱わず、未使用ファイルが残るだけ。
異常終了で未参照ファイルが残っても、起動時はstore.jsonが参照する履歴だけを読む。
電源断に対する完全な耐久性を保証する構成ではない。

参照ファイルが欠損・破損していたら空の履歴として起動せず、STORAGE_ERRORで停止する。
内容のハッシュ、ファイルパス、Contact所属、メッセージ保存順を検証する。

## 移行

Backendを停止して新コードを起動すると、旧形式を検証した後に
store.legacy-<UUID>.jsonへバックアップし、初回のみ分割形式へ移行する。
移行の切替に失敗した場合は旧store.jsonを保持する。設定・API・Frontendの変更は不要。

2026-10-17のローカル実データ移行では、Contact 4件・Conversation 4件・Message 36件・
Reminder 1件・Tab 3件について、移行前後と再読み込み後の完全一致を確認した。
これは移行時点の件数であり、その後の受信・操作によって増減する。

## バックアップと復旧

Backendを停止し、**data/全体**をコピーする。分割後はstore.json単体では履歴を復元できない。
旧形式へ戻す場合も、最初に現在のdata/全体を退避し、旧形式バックアップのコピーをstore.jsonへ置く。
新コードで起動すると再び分割形式へ移行する。
起動中の手作業でのファイル変更・削除はしない。data/とバックアップはGit管理外で保持する。

### 画像の保存先

画像は `data/media/line/<画像ID>.png|jpg`、`data/media/slack/<画像ID>.png|jpg` のようにプラットフォーム別に保存します。現在、画像の送受信に対応しているのはLINEのみです。所属を判定できない旧画像は `data/media/unassigned/` に保管します。

ブラウザ用の `/api/media/:id` とLINE配信用の `/media/:id` は変更しません。保存先はBackendがIDから解決し、移行前の `data/media/` 直下の画像も読み取れるため、履歴の画像URLを変更する必要はありません。画像のIDやパスを手動で変更しないでください。
