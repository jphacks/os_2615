## 製品概要

### 背景(製品開発のきっかけ、課題等）

企業の問い合わせ窓口やイベント運営など、連絡先によってLINEとSlackを使い分ける業務では、メッセージを確認するためにアプリを行き来します。しかし、届いたことを把握していても、「誰にまだ返信していないか」「確認してから返すつもりだった相手は誰か」は、担当者の記憶に頼りがちです。

こねくとは、**複数のサービスに分かれた連絡を、人と返信状況を軸に整理する**ために開発しました。対応サービスの数を増やすことよりも、LINEとSlackの両方から実際に受信し、同じ画面から返信できる体験を優先しています。

### 製品説明（具体的な製品の説明）

こねくとは、**LINE公式アカウントに届く1対1メッセージと、Slack Botに届くDMを、共通のInboxで管理・返信するWebアプリ**です。

会話の確認から返信、返信忘れの防止、日時を指定した予約送信までを一つの画面で行えます。PC・スマートフォンに対応し、用途別のタブやサービス別フィルタで相手を探せます。

> 現在の接続対象は、設定したLINE公式アカウントとSlack Botに届くメッセージです。個人のLINEアカウントやSlackユーザーの全DMを取り込む機能ではありません。同名でもLINEとSlackの相手は別Contactとして扱い、自動で同一人物に統合しません。

### 特長

#### 1. LINEとSlackの受信・返信を、一つのInboxで完結

LINE公式アカウントとSlack BotのDMを同じ画面で確認・返信できます。LINEは画像の受信・表示・ダウンロードと、JPEG／PNG画像の送信（1枚・1MBまで）にも対応しています。

#### 2. 未返信・リマインダー・予約送信で、返信漏れを減らす

- **未返信：** 新着メッセージを受けると未返信になり、返信または「対応済み」操作で解除します。
- **後で返信：** 指定時刻に会話を強調し、画面内のリマインダーで知らせます。
- **予約送信：** 最大14日先まで本文と送信日時を予約でき、送信前は取り消せます。

リマインダーはアプリを開いている間の画面内通知です。予約送信はBackendの稼働が必要で、停止中に予定時刻を過ぎた予約は送信しません。

#### 3. タブ・検索・サービス別フィルタで、必要な相手をすぐに探す

「すべて・未返信・後で返信・お気に入り」に加え、用途別のタブを作成できます。タブは名前変更、ドラッグまたはボタンでの並び替えに対応し、同じ相手を複数のタブに登録できます。

「すべて・LINE・Slack」のドロップダウンと名前検索を組み合わせて絞り込めます。検索はひらがな・カタカナ・半角カナの表記揺れに対応し、漢字の読みは検索用の名前として手動登録できます。

文字サイズ・ライト／ダークテーマ・タブの移動方法は端末ごとに設定できます。

### 解決出来ること

- **アプリを行き来する手間を減らす：** LINEとSlackの受信確認・履歴参照・返信を一つの画面へまとめます。
- **返信すべき相手を見つける：** 未返信フィルタと返信時刻の設定で、確認したまま返し忘れる状況を減らします。
- **連絡先を用途で整理する：** サービスに縛られないタブへ相手を登録し、必要な連絡先を探しやすくします。

### 今後の展望

こねくとは、**企業が複数のメッセージサービスに分かれた連絡を一元管理する、企業向けアプリ**を目指しています。まずは問い合わせ窓口やイベント運営など、現在の接続範囲に合う業務で、使いやすさと返信漏れ防止の効果を検証します。

将来的には、Providerを分離した構成を活かし、**Microsoft Teams・Discord・Instagramなどへの接続拡張**を目指します。各サービスのAPI提供範囲・権限・利用条件に応じて接続方法を検討します。これらのサービスへの接続は現時点では未実装です。

企業での継続利用に向けて、認証・担当者ごとの権限管理・公開環境も整備する予定です。現在は単一Backend・共有InboxのMVPであり、これらのアクセス管理は未実装です。

### 注力したこと（こだわり等）

* **「集める」だけで終わらないこと。** 外部サービスへの実際の返信、未返信状態の更新、後で返信の完了までをつなぎ、LINEとSlackの両方で動作確認しました。2台の端末からのアクセス・送信、再起動後の設定保持、通信失敗時の入力保持も確認しています。
* **2人で並行開発できる境界。** 共通データ構造・APIを先に決め、Backendを`src/`、Frontendを`frontend/`へ分離しました。外部サービス固有のJSONはProvider内で共通形式へ変換し、UIや共通Serviceへ持ち込まない構成です。
* **失敗しても状態を壊しにくいこと。** LINE署名のraw body検証、重複受信の抑制、Slack Bot自身のイベント除外、同じ会話の並行送信防止を実装しています。送信結果が不明な場合は自動再送せず、入力文を残して送信先の確認を促します。


#### セキュリティ・バイ・デザイン

メッセージや個人情報を扱うため、**外部から届く入力を信用せず、安全な表示・受信検証・保存データの整合性確認を設計に組み込む**方針で開発しました。

* **XSS対策：** 本文・表示名・タブ名をHTMLとして挿入せず、Reactでテキストとして表示します。画像URLを所定の形式に制限し、公開プレビューにはCSPを設定しています。[公開プレビュー設定](frontend/vite.config.js)
* **保存データの整合性確認：** 分割したJSONファイルをSHA-256チェックサムとデータ間の関連で検証し、不一致・欠損時は起動を中止します。破損や予期しない変更の検知を目的とし、管理情報ごと書き換えられた場合の真正性は保証しません。[分割保存処理](src/repositories/splitStore.js)
* **受信経路と秘密情報の保護：** LINE WebhookはJSON解析前のraw bodyでHMAC-SHA256署名を検証します。Token・SecretはBackendの環境変数から読み込み、Frontend・Git・エラーログへ含めない構成です。

現在は認証・利用者ごとの権限管理を持たないMVPです。上記の対策だけで企業向けの安全性が完結するとは考えず、継続的な外部公開に向けてアクセス管理を整備します。

## 開発技術

### 活用した技術

#### API・データ

* **LINE Messaging API：** Webhookによる受信、プロフィール取得、Push Messageによる返信。Channel SecretでHMAC-SHA256署名を検証します。
* **Slack API / Socket Mode：** `message.im`によるDM受信、ユーザー情報取得、`chat.postMessage`による返信。Slack用の公開Webhook URLは不要です。
* **ローカルJSONによる永続化：** メッセージをサービス・Contactごとのファイルへ分割し、共通情報とファイル参照を`store.json`で管理します。画像もサービス別に保存し、履歴・お気に入り・リマインダー・タブ・予約情報はBackend再起動後も保持します。

#### フレームワーク・ライブラリ・モジュール

* **Backend：** Node.js 22以上、JavaScript、Express、`@slack/bolt`、dotenv。
* **Frontend：** React、Vite、lucide-react、CSS。
* **検証：** Node.js標準のテストランナーで、保存処理・送受信・予約送信・Frontendの各処理を検証しています。
* **開発時の外部受信：** ngrokでLINE WebhookをローカルBackendへ転送します。

#### デバイス

* **サーバー：** 開発用MacでBackend・Frontendを起動します。現在は単一Backendプロセス・共有のInboxを前提としたMVPです。
* **利用端末：** PC・スマートフォンのブラウザ。同じネットワーク内の2端末からアクセス・送信を確認しています。端末ごとにデータを持つのではなく、同じBackendのデータを参照します。

### 独自技術

#### ハッカソンで開発した独自機能・技術

* **共通Messageへの変換とサービス別の送信処理：** LINE・Slackの差をProviderとMapperへ分離し、共通のInbox・履歴・返信APIを構築しました。[LINE Provider](src/providers/line/) / [Slack Provider](src/providers/slack/) / [ReplyService](src/services/replyService.js)
* **会話単位の状態管理と柔軟な分類：** 未返信・リマインダー・お気に入り・任意タブを組み合わせ、サービスをまたいだ連絡先の整理を実装しました。[Message Repository](src/repositories/messageRepository.js) / [タブ保存処理](src/repositories/tabRepository.js) / [名前検索](frontend/src/services/contactSearch.js)
* **相手別ファイルと管理ファイルを使う保存処理：** 変更した履歴を先に保存し、管理ファイルの置換で更新を確定します。旧形式のバックアップ・移行、ファイル欠損や保存失敗の検証も実装しました。[分割保存処理](src/repositories/splitStore.js) / [保存処理のテスト](tests/splitStore.test.js) / [保存形式・復旧手順](docs/storage.md)

<summary>ローカルでの起動・デモ確認</summary>

Node.js 22以上を用意し、リポジトリのルートで依存関係を導入します。

```sh
npm install
npm install --prefix frontend
cp .env.example .env
```

`.env`に以下の値を設定します。Token・SecretはFrontendへ設定せず、Gitへ追加しません。

```dotenv
LINE_CHANNEL_ACCESS_TOKEN=
LINE_CHANNEL_SECRET=
SLACK_BOT_TOKEN=
SLACK_APP_TOKEN=
```

別々のターミナルでBackendとFrontendを起動します。

```sh
# Backend：管理API 3000 / LINE Webhook 3001
npm start
```

```sh
# Frontend：5173
npm run dev --prefix frontend
```

ブラウザで`http://127.0.0.1:5173/`を開きます。画面は実APIへ接続し、初期データは空です。

LINEの新着を受信する場合は、さらに`ngrok http http://127.0.0.1:3001`を起動し、表示されたHTTPS URLに`/webhooks/line`を付けてLINE側のWebhook URLへ設定します。SlackはSocket Modeで接続します。外部サービスとの送受信にはインターネット接続が必要です。

データはGit管理外の`data/`へ保存されます。バックアップはBackendを停止して`data/`全体を保存してください。

詳しい起動方法、スマートフォンからのアクセス、デモと復旧の流れは[デモ手順](docs/demo.md)を参照してください。

ホーム画面へ追加するPWA設定も用意し、iPhoneでの起動・返信を確認しています。HTTPSでのインストール確認は[PWA手順](docs/pwa.md)を参照してください。インストール後もBackendへの接続が必要です。
